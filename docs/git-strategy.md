## Выбранная стратегия: GitHub Flow

### Обоснование

Проект небольшой (один разработчик), без сложного релизного
цикла. Используется упрощённая модель GitHub Flow:

- `main` — всегда стабильная, готовая к деплою версия;
- `feature/*` — короткоживущие ветки под конкретную задачу;
- `bugfix/*` — ветки для исправления найденных багов;
- `release/*` — ветки для подготовки релиза.

Классический Git Flow с `develop` избыточен для одиночного
учебного проекта: добавляет синхронизацию между `develop` и
`main` без реальной пользы. GitHub Flow проще, история чище,
CI работает на каждый push.

### Правила

1. Любая новая функция — в отдельной ветке `feature/<имя>`.
2. Любой баг — в отдельной ветке `bugfix/<имя>`.
3. Коммиты осмысленные, в прошедшем времени, на русском:
   - ✅ «Добавлен модуль exceptions»
   - ❌ «фикс», «правки»
4. После завершения — слияние в `main` через fast-forward
   или merge-коммит.
5. `main` всегда проходит тесты (35/35) и CI (GitHub Actions).
6. Тег `vX.Y.Z` ставится только на стабильный `main`.
